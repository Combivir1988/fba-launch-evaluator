# Implementation Plan: Ценовой диапазон анализа

**Branch**: `main` | **Date**: 2026-09-19 | **Spec**: [spec.md](spec.md)

## Summary

Менеджер задаёт коридор цен («от» / «до»). Перед расчётами строится отфильтрованный «вид» на листинги (Xray, при его отсутствии — POE), и все конкурентные расчёты идут по нему; показатели спроса, сегменты цен, уровень данных и статус выручки 1a считаются по всей нише. В результатах появляется сводка `priceBand` — её читают дашборд, автономный HTML, публичные ссылки и AI-пейлоад. Сервер, база и API не меняются.

## Technical Context

**Language/Version**: браузерный JavaScript ES2022 + Node 22 (тесты); расчётное ядро `shared/` общее
**Primary Dependencies**: без новых зависимостей
**Storage**: два новых поля во входных данных анализа (`inputs.priceMin`, `inputs.priceMax`) — хранятся в `core` общей истории (spec 002), миграция схемы БД не нужна
**Testing**: `node --test` на реальных фикстурах (Xray 2026-08-21, POE 2026-09-15) + jsdom-рендер + Playwright-проба
**Project Type**: тот же web-service, изменения только в `shared/`, `public/`, `tests/`
**Performance Goals**: пересчёт ≤ 100 мс на 500 листингах (один дополнительный проход фильтра + второй расчёт конкуренции для сравнения)
**Constraints**: при пустом диапазоне результаты совпадают с текущими побайтно, кроме нового поля `results.priceBand` (SC-002); 137 существующих тестов остаются зелёными
**Scale/Scope**: 1 новый модуль ядра, правки в 5 модулях ядра, рендерере, панели, справке; ~12 новых тестов

## Ключевые решения (D1–D8)

- **D1 — Фильтр как «вид» перед расчётами.** `applyPriceBand(p)` возвращает копии `xray` и `poe` с отфильтрованными `asins` / `asinMetrics`; модули конкуренции получают вид и не меняются по логике. Так гарантируется, что ни один конкурентный показатель не «забудет» про фильтр.
- **D2 — Что по виду, что по всей нише.** По виду: `competition`, `criterion1` (кроме 1a и спроса), `challenger`, зависящие оси `scorecard`, топ конкурентов в AI-пейлоаде, таблица конкурентов. По всей нише: `traffic` (включая концентрацию кликов POE), `gate0` (уровень данных), `priceSegments`, 1a и стоп-вопрос выручки, 1c, 1g, 1h. У POE фильтруется только `asinMetrics`; запросы, тренды, launchPotential, отзывы-темы остаются целыми.
- **D3 — 1a по всей нише, выручка диапазона справочно.** Порог 1a описывает размер рынка. В `items["1a"]` добавляются `bandValue` и `bandShare`; статус и счёт «N из 8» не зависят от ширины коридора.
- **D4 — Уровни выборки.** `ok` (≥ 15), `small` (5–14: предупреждение), `insufficient` (< 5: вид пустой → конкурентные показатели «нет данных»). Пороги — в `thresholds.priceBand`, редактируются во вкладке «Пороги».
- **D5 — Сравнение с нишей.** Сводка хранит показатели всей ниши (доля топ-бренда, топ-5, медиана цены, отзывы) — второй вызов `competition` по целым данным; дёшево и даёт менеджеру контекст «в коридоре лидер держит 41 %, в нише — 18 %».
- **D6 — Порядок фильтров:** исключённые бренды и «мои ASIN» работают как раньше внутри модулей; диапазон применяется раньше них к списку листингов. Листинг без цены в диапазон не входит и считается в `noPrice`.
- **D7 — Некорректный диапазон не применяется** (`min > max`, отрицательные, нечисловые): `summary.valid=false`, расчёт по всей нише, поля подсвечены.
- **D8 — Совместимость:** `priceMin/priceMax = null` по умолчанию; `migrate` подставит их старым документам; при пустом диапазоне `compute` идёт прежним путём (вид = исходные данные, без копирования), результаты идентичны; `METHODOLOGY_VERSION` повышается.
