# Контракт: правила отбора осей и вариантов (spec 025)

Формулы и пороги. Числа выбраны замером (research.md D2, D3) и живут константами в ядре рядом с правилом — в настройки не выносятся: они описывают устройство рынка, а не вкус человека.

## 1. Семьи вариаций

Семья — множество листингов с общим `parentAsin`. Листинг без родителя — семья из одного.

```
families.multi        = число семей размером >= 2
families.revenueShare = выручка семей размером >= 2 / выручка всех листингов
```

Выручка листинга — та же, что везде в этапе 2: `asinRevenue`, иначе `price × asinSales`, иначе 0.

## 2. Частота смены поля (кандидат в оси)

Для поля `f` и семьи `F` (|F| ≥ 2):

```
меняется(f, F) = | { значение f у листингов F, кроме пустых } | >= 2
rate(f)        = | { F : меняется(f, F) } | / | { F : |F| >= 2 } |
```

Пустое значение («нет данных») не считается отдельным значением: иначе неполнота таблицы выглядела бы как вариативность.

**Порог**: `AXIS_RATE_MIN = 0.20`.

Обоснование — замер: 65 полей из 207 имеют два и более весомых значения при частоте ниже 20 %. Это поля, делящие рынок, а не линейку: «Управление» в нише автоматических бросателей мяча меняется в **0 %** семей — на рынке есть кнопка и пульт, но ни одна марка не делает оба в одной карточке.

## 3. Весомое значение

Доля считается от выручки **ПОЛЯ**, а не всей ниши — то есть только по листингам, где поле заполнено:

```
fieldRevenue(f)   = Σ выручка(a) по листингам a, где f заполнено
valueShare(f, v)  = Σ выручка(a) по листингам a со значением v / fieldRevenue(f)
весомое(f, v)     = valueShare(f, v) >= VALUE_SHARE_MIN
```

**Порог**: `VALUE_SHARE_MIN = 0.10`.

Обоснование — замер по самой сильной оси: 10 % даёт медиану 3 значения (максимум 4), 5 % даёт 5 (максимум 7), 15 % даёт 2 и в 7 нишах из 18 меньше двух. У лидеров медиана 5 ASIN, но лидер копил линейку годами, а речь о старте.

**Знаменатель здесь — главное.** Первая попытка считала долю от выручки всей ниши и складывала значения всех осей: получалось 36 значений медианой. Предложить 36 ASIN нельзя.

## 4. Ось годится — ОДНО правило, а не два шага

```
ось(f) = rate(f) >= AXIS_RATE_MIN  И  | { v : весомое(f, v) } | >= MIN_HEAVY_VALUES
```

**Порог**: `MIN_HEAVY_VALUES = 2`.

Второе условие — защита от поля, где у каждого листинга своё уникальное значение: такое поле меняется почти в каждой семье и получает максимальную частоту, но осью линейки не является. Живые случаи: «Уникальные фичи» (95,8 % семей, 334 разных значения, весомых — **ноль**) и «Аромат» (95,8 %, 328 значений, весомых — **ноль**).

Поле, прошедшее частоту и не прошедшее второе условие, попадает в `axisRejected` с причиной — отказ обязан быть виден.

## 5. Выбор оси для линейки

```
выбранная = первая по убыванию rate среди прошедших правило (4)
```

При равной частоте — больше весомых значений, затем имя поля по алфавиту: порядок обязан быть устойчивым, иначе один и тот же анализ при двух открытиях даст разные линейки.

Прочие прошедшие оси показываются списком без цен и без вариантов (D4).

## 6. Состав линейки

```
главный  = конфигурация из config.priceChoice (по умолчанию доминанта по каждому полю)
варианты = весомые значения выбранной оси, кроме значения главного,
           по убыванию valueShare
```

Вариант отличается от главного **ровно по одной оси**: остальные поля берутся у главного без изменений. Сочетание двух осей не предлагается — 3 × 3 дало бы 9 сочетаний, каждое с ценой на одном-двух аналогах.

## 7. Цена варианта

Считается существующим расчётом цены конфигурации для сочетания «конфигурация главного, у которой значение выбранной оси заменено на значение варианта». Берутся: рыночная цена, вход, потолок, число аналогов, уровень совпадения, признак отката к области.

```
price = null,  если аналогов под сочетание не нашлось
```

Цена НЕ выдумывается и НЕ заменяется ценой главного. `priceNote` называет причину.

## 8. Спрос из ключей

```
искать(v) = значение v текстовое И записано латиницей
```

Числовые и размерные значения **не ищутся вовсе**: сопоставлять «12» или «3» со словом в ключах бессмысленно, «20x20x1» распадается на мусор. Замер: у числовых 83,0 % без найденного объёма против 39,0 % у латиницы.

```
sv(v) = Σ объём поиска фраз, содержащих слово значения v,
        среди фраз, не помеченных ASIN и не брендовых
```

Бренды отсеиваются существующим матчером по границе слова (spec 023) — своё правило не заводится.

Три состояния различаются в тексте и это обязательно:

| Состояние | Что значит |
|---|---|
| не искали | числовое значение, либо выгрузки ключей нет |
| искали, не нашли | слово в ключах не встречается |
| ноль | в ключах встречается с нулевым объёмом |

Слово из ключей, которого нет среди значений полей, **не может породить вариант** — это ворота SC-002.

## 9. Правила отсутствия

| Условие | `status` |
|---|---|
| нет выгрузки Xray | `no_xray` |
| нет семей размером ≥ 2 | `no_variations` |
| есть семьи, нет таблицы характеристик | `no_stage2` |
| ни одно поле не меняется ни в одной семье | `no_differences` |
| есть кандидаты по частоте, ни один не набрал двух весомых значений | `no_repeating` |
| ось выбрана | `ok` |

Каждый статус несёт собственную человеческую фразу. Склеивать их нельзя: причины разные, и выводы человека из них разные.
