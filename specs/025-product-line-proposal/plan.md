# Implementation Plan: предлагаемая товарная линейка

**Branch**: `main` (отдельной ветки не заводим, как в спеках 019–024) | **Date**: 2026-11-16 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/025-product-line-proposal/spec.md`

## Summary

Этап 2 отвечает «какой ОДИН товар делать», а 88,6 % денег ниши принадлежат семьям из нескольких вариаций (замер на 67 живых нишах; у ТОП-10 лидеров медиана 5 ASIN, одиночек 10 %). Иерархию семей приложение уже разбирает и нигде не читает.

Работа: новый чистый модуль в ядре находит **оси вариации** (характеристики, меняющиеся внутри одной карточки), выбирает самую сильную и предлагает **главный товар плюс 3–4 варианта** по ней, с ценой каждого из уже существующего расчёта цены конфигурации. Блок показывается в этапе 2 **после ТЗ**, вырезается из публичной ссылки и автономного HTML, и **не трогает ни одного вычисления этапа 1**.

## Порядок работ

### 1. Базовый замер «до» — ПЕРВОЙ задачей, до единой правки в `shared/`

`method_hash` (`server/stats.js:24`) — sha256 по содержимому ВСЕХ `shared/*.js`. Первая же правка стирает прежние цифры. Снять чтением живой базы **без единой записи**: вердикты, статусы Критерия 1, Scorecard и контрольные отпечатки по всем живым анализам. Фикстура **без названий ниш** (как `brand-baseline.json` в spec 023, `dist-baseline.json` в spec 024).

### 2. Ворота SC-003 — исключение поля из отпечатка ДО появления поля

`tests/helpers/results-hash.js`: `productLine` исключается как добавочное. Делается **раньше** появления поля в расчёте, иначе первый прогон уронит отпечаток и падение получит две возможные причины вместо одной (D11). Отпечаток обязан остаться прежним на ВСЕХ фикстурах.

### 3. Ворота SC-001 и SC-002 тестами, до реализации

- **SC-001**: ниша, где ни одна ось не набирает двух весомых значений, даёт явный ответ «линейку здесь не строят» и НОЛЬ вариантов. Отдельно — три разных исхода из D5 различимы. Проверяется подстановкой: реализация, выбирающая осью поле из сотен уникальных значений, роняет тест.
- **SC-002**: слово из ключей, отсутствующее среди значений полей, не порождает варианта. Подстановка: реализация, предлагающая `duct` в нише joist tape, роняет тест.

### 4. Ядро: оси вариации (US1)

Новый `shared/product-line.js`. Семьи из `parentAsin`; ось — поле, меняющееся внутри семьи. Правило отбора — **одной операцией** (D1): ось годится, если частота ≥ 20 % семей (D2) И внутри неё ≥2 значения с долей ≥10 % выручки поля (D3). Возврат: список осей с числами, самая сильная отмечена, и один из трёх исходов D5, если осей нет.

### 5. Ядро: предложенная линейка (US2)

Главный товар — конфигурация из `config.priceChoice` (по умолчанию доминанта, FR-020). Варианты — значения самой сильной оси, кроме значения главного, каждый отличается ровно по одной оси (D4). Цена каждого — `priceByConfig` с подменённым значением этой оси; оттуда же `analogs`, `tier`, `matchWords`, `fallback`. Нет аналогов — цены нет, сказано прямо (FR-008).

### 6. Поле в результат — ОТДЕЛЬНОЙ задачей

`results.productLine` дописывается в **ЯВНЫЙ перечень ключей** сборки результата. Это отдельный пункт намеренно: поле, которого нет в перечне, молча не доедет до интерфейса и ни один тест не упадёт (прецеденты: `launchPlan` spec 020, `reviewBarrierEffective` spec 022).

### 7. Вырезание из публичной ссылки и автономного HTML + ворота SC-005

`stripProductLine(a)` рядом со `stripStage3(a)`, вызывается на обоих путях. Ловушка утечек по образцу `findStage3Leaks`. Проверяется СОДЕРЖИМЫМ снимка, а не кодом показа (D7).

### 8. Секция в интерфейсе (US1, US2, US3)

Новая секция в реестре `SECTIONS` **после** `["tz", secTz]` и в наборе `STAGE2`. Показывает: вывод о линейке, список осей с числами, таблицу предложенных товаров (ось, значение, доля выручки, листингов, цена аналогов, число аналогов, премия, поисковый объём). Если этап 2 не выполнен — то, что известно из Xray, и прямо названо, чего не хватает (FR-017).

### 9. Спрос из ключей (US4, P2)

Поисковый объём только для текстовых значений латиницей; для числовых не ищется и сказано почему; бренды отсеиваются существующим `brandMatcher` (D9).

### 10. Тексты, подсказки, Справка

Пояснения при наведении у всех новых величин; `tests/tips.test.js` зелёный. Карточка в Справке: чем ось линейки отличается от характеристики товара и почему поле «Управление», меняющееся в нуле семей, осью не является.

### 11. Живая проверка после развёртывания

Сверка с базовым замером: вердикты — 0 изменений, Критерий 1 и Scorecard — 0, отпечаток не сдвинулся. Плюс: в скольких нишах оси найдены, в скольких «линейку не строят», сколько вариантов предлагается (ожидание — медиана 3, максимум 4), у скольких вариантов есть цена и поисковый объём.

**MVP = пункты 1–8.** Пункт 9 (US4) можно выпустить отдельно — его эффект меряется независимо.
