# Research: Командная работа и публичные ссылки (spec 002)

Дата: 2026-09-19. Все пункты Technical Context разрешены, маркеров NEEDS CLARIFICATION нет.

## R1 — Где хранить данные бесплатно

- **Decision**: PostgreSQL на Neon, план Free; подключение через `pg` по `DATABASE_URL` (pooled-хост `-pooler`, `sslmode=require`).
- **Rationale**: проверено 2026-09-19 по страницам тарифов. Neon Free: $0 бессрочно, без карты, 0.5 GB на проект, 100 CU-часов/мес, автосон через 5 мин простоя (не отключается). Railway Free: $1 кредита/мес, 0.5 GB RAM на сервис; приложение потребляет ≈ $0.36/мес (замер за 48 ч: RAM avg 35 MB, max 192 MB, CPU ≈ 0). База на Railway работала бы круглосуточно: только 256 MB RAM = $2.5/мес — не помещается в кредит.
- **Следствия**: после простоя первый запрос к БД +0.5–2 с (пробуждение). `/api/health`, статика и страница входа БД не трогают, чтобы база спала. 100 CU-часов при 0.25 CU = 400 часов активной работы в месяц — для команды до 10 человек с запасом. Пул: `max: 5`, `idleTimeoutMillis: 30 000`, `connectionTimeoutMillis: 10 000`, обработчик `pool.on("error")` (Neon рвёт простаивающие соединения), один повтор запроса при ошибке соединения.
- **Проверено вживую 2026-09-19**: проект Neon создан (eu-central-1, Postgres 18, pooled-хост), подключение через `pg` 8 — 2.7 с с пробуждением, 28 мс «тёплый» запрос, пустая база 7.7 MB. Строка Neon содержит `sslmode=require&channel_binding=require`: (1) `pg` предупреждает, что в v9 `require` ослабнет → в `server/db/index.js` заменять на `sslmode=verify-full`; (2) символ `&` ломает `source` env-файла без кавычек → значение в файле секретов хранится в одинарных кавычках.
- **Alternatives considered**: Postgres на Railway (платно после триала); SQLite на томе Railway (том 0.5 GB на Free есть, но привязка к одному хосту, нет бэкапов, данные в зоне риска при смене тарифа); Supabase Free (проект ставится на паузу после 7 дней неактивности — хуже автосна Neon); Turso/libSQL (другой диалект SQL, хуже с JSONB); хранение в файлах на диске контейнера (теряется при деплое).

## R2 — Размер документа и схема хранения

- **Decision**: документ делится на `core` (JSONB) и `aggregates_gz` (BYTEA, gzip JSON). Метаданные для списка — в колонках.
- **Rationale**: замер на фикстурах — весь документ 2 088 KB raw / 177 KB gzip, из них Cerebro 1 907 KB (4 350 ключей; у владельца бывает 9 000 → ~4 MB raw). `core` = всё, кроме `aggregates` (inputs, thresholds, sources, results, ai, patents) ≈ 30–60 KB. Ползунки, AI и патентный скан меняют только `core` → автосохранение шлёт ≤ 60 KB. `aggregates` меняются только при загрузке/удалении файлов и пересчёте кластера Cerebro → отдельный запрос с телом до 12 MB. JSONB для `aggregates` не нужен (по ним нет запросов), а gzip в приложении сжимает лучше TOAST (pglz) примерно вдвое.
- **Бюджет места**: ~0.3 MB (aggregates) + ~0.05 MB (core) + снимки ссылок ~0.04 MB → ≥ 1 300 анализов в 0.5 GB. Админу показывается заполнение (`pg_database_size`), предупреждение с 80 %. Сырые ключи Cerebro храним: без них коллега не пересоберёт кластер. Резерв на будущее — хранить только ключи с SV ≥ порога.
- **Alternatives considered**: один JSONB-документ (каждое движение ползунка = запись 2–4 MB, быстрый износ лимита и трафика); не хранить Cerebro вовсе (ломает пересчёт кластера на другом устройстве); объектное хранилище для агрегатов (ещё один сервис).

## R3 — Хэширование паролей

- **Decision**: `crypto.scrypt`, N=2^15, r=8, p=3, соль 16 B, ключ 64 B, `maxmem` 64 MB; формат `scrypt$15$8$3$<salt b64>$<hash b64>`; сравнение `timingSafeEqual`. Все вызовы идут через очередь по одному.
- **Rationale**: встроено в Node (ноль зависимостей, нет нативной сборки в Docker); параметры — из рекомендаций OWASP для scrypt (вариант N=2^15, p=3). Один вызов занимает ~33 MB — очередь гарантирует потолок при лимите 0.5 GB RAM даже при переборе. Параметры в строке хэша позволяют усилить их позже и перехэшировать при входе.
- **Alternatives considered**: argon2 (`argon2`/`@node-rs/argon2` — нативные бинарники, лишняя зависимость); bcrypt (то же + слабее по памяти); PBKDF2 (слабее против GPU).

## R4 — Сеансы

- **Decision**: непрозрачный случайный токен 32 B; cookie `fba_sid` — `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=30 дней` (скользящее продление раз в сутки); в БД — SHA-256 токена, user_id, срок, last_seen. Кэш результата проверки в памяти на 60 с. Отключение пользователя, сброс и смена пароля удаляют его сеансы.
- **Rationale**: серверные сеансы отзываются мгновенно (JWT — нет); HttpOnly защищает от кражи через XSS (сейчас токен лежит в localStorage); кэш 60 с выполняет FR-008 («≤ 1 минуты») и не будит Neon на каждый запрос; `EventSource` отправляет cookie сам → токен уходит из URL и логов. `Secure` отключается только при `NODE_ENV≠production` (localhost).
- **Alternatives considered**: JWT без состояния (нельзя отозвать без чёрного списка); `express-session` + store (зависимости ради 60 строк кода); токен в localStorage (как сейчас — уязвим к XSS, светится в URL SSE).

## R5 — CSRF и перебор

- **Decision**: для POST/PUT/PATCH/DELETE — обязательны `Content-Type: application/json`, `X-Requested-With: fba`, `Origin`/`Referer` с тем же хостом. Вход: счётчик неудач в `users` (5 подряд → блок на 15 мин), плюс существующий IP-лимитер (10 попыток/10 мин); для неизвестного логина — фиктивный scrypt и то же сообщение «Неверный логин или пароль».
- **Rationale**: SameSite=Lax уже блокирует межсайтовые POST; пользовательский заголовок нельзя выставить без CORS-разрешения, которого сервер не даёт. Хранение счётчика в БД переживает перезапуск.
- **Alternatives considered**: CSRF-токены (избыточно для JSON-API с одного origin); капча (внешний сервис).

## R6 — Конфликты одновременного редактирования

- **Decision**: оптимистичная блокировка — `UPDATE … WHERE id=$1 AND version=$base RETURNING version`; 0 строк → `409 {updatedBy, updatedAt, version}`. Клиент показывает диалог: «Сохранить как копию» (новый id, автор — текущий), «Перезаписать» (повтор с `force` и актуальной версией), «Открыть свежую версию».
- **Rationale**: проверено на PGlite (спайк 2026-09-19). Соответствует FR-015 без блокировок и без realtime. `core` и `aggregates` разделяют одну версию — конфликт ловится при любой записи.
- **Особый случай**: сервер сам пишет результат задачи (R9) и повышает версию. Чтобы пользователь не получил ложный конфликт с самим собой, SSE-событие `done` несёт новую `version`, клиент принимает её как базовую; запись результата задачи делается точечно (`jsonb_set` по ключу `ai`/`patents`) и не затирает остальной `core`.
- **Alternatives considered**: блокировка «анализ открыт другим» (зависшие блокировки, нужен heartbeat); CRDT/realtime (вне объёма); последний побеждает (нарушает FR-015).

## R7 — Публичная ссылка: токен, выдача, приватность

- **Decision**: токен — 32 B `randomBytes` в base64url (43 символа, 256 бит), адрес `/s/<token>`. `GET /s/:token` отдаёт одну и ту же статическую `share.html` для любого токена; данные — `GET /api/public/shares/:token`. Несуществующая, отозванная и истёкшая ссылки → одинаковый `404 {error:"link_unavailable"}` и один текст: «Ссылка недействительна: её не существует, она отозвана или истёк срок действия». Заголовки: `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`; `robots.txt` с `Disallow: /s/`. Лимит 60 запросов/10 мин на IP.
- **Rationale**: 256 бит перебрать невозможно, лимитер — защита от шума и подсчёта просмотров ботами. Одинаковая HTML-оболочка не раскрывает ничего до запроса данных. Токен хранится открыто: снимок лежит в той же БД, хэширование не добавляет защиты, зато ссылку можно показать и скопировать повторно.
- **Просмотры**: считаются на запросе данных; повтор с того же IP по той же ссылке в течение 30 мин не считается; запросы с действующим сеансом команды не считаются.
- **Alternatives considered**: подписанный URL без хранения (нельзя отозвать и считать просмотры); пароль на ссылку (в спецификации осознанно отказались); отдельный поддомен (DNS и сертификаты — лишнее).

## R8 — Снимок и режим «без закупочной экономики»

- **Decision**: чистая функция `shared/share-snapshot.js → buildSnapshot(analysis, {mode, preparedBy, snapshotAt})`. Полный режим: документ без `aggregates.cerebro.keywords` и без служебных полей (≈ 180 KB raw / 40 KB gzip). Режим `no_economics`: дополнительно удаляются экономические входы, `results.economics`, `results.budget`, экономические стоп-вопросы, числовые комментарии критериев 2 и 6 (остаётся статус), ось экономики scorecard остаётся баллом без расшифровки; тексты AI фильтруются по предложениям (лексика: себестоим, COGS, марж, прибыл, ROI, бюджет, закуп, ACOS, CPC-экономика, суммы в $ рядом с ними). Финальная страховка: в сериализованном снимке ищутся значения COGS, маржи, прибыли/ед., ROI, бюджета (в форматах `12.5`, `12,5`, `12.50`, `1 250`, `%`); поле, где найдено, удаляется целиком. `render.js` получает `snapshot.hidden = ["economics","budget",…]` и не рисует эти секции.
- **Rationale**: данные, которых нет в ответе сервера, нельзя достать из исходника страницы или скачанного HTML (FR-025, SC-006). Функция в `shared/` тестируется без сервера на реальных фикстурах и mock-вердикте.
- **Alternatives considered**: скрывать CSS/условием рендера (данные остаются в JSON — нарушение FR-025); перегенерировать AI-блок без экономики (платный вызов и 3–6 минут на каждую ссылку); вырезать AI-блок целиком (теряется основная ценность для получателя).

## R9 — Задачи: лимиты, запись результата, журнал

- **Decision**: задачи остаются в памяти процесса (`server/jobs.js`), к `meta` добавляются `userId`, `analysisId`. Перед стартом проверка: идёт ли задача того же типа у пользователя → `429 user_limit`; по тому же анализу → `429 analysis_limit` (с именем запустившего); всего ≥ `MAX_JOBS` (4) → `429 global_limit`; ответ содержит список идущих задач. По завершении сервер сам пишет результат в анализ (для AI — после `reconcile` с `results` из сохранённого `core`), затем шлёт `done` с новой версией. `GET /api/analyses/:id/jobs` возвращает идущие задачи по анализу → подхват с любого устройства. Журнал `job_log`: строка при старте, обновление при финише; при старте процесса все `running` → `interrupted`.
- **Rationale**: один инстанс и дренаж 300 с при деплое уже есть; переносить сами задачи в БД не нужно — поток от провайдера AI нельзя возобновить после перезапуска. Запись результата сервером закрывает найденный 2026-09-18 класс ошибок «результат жил только в памяти вкладки».
- **Требование к клиенту**: перед запуском задачи анализ должен быть сохранён (клиент делает flush автосохранения), иначе серверу некуда писать результат.
- **Alternatives considered**: очередь в БД с воркером (сложно и не нужно при одном инстансе); ставить в очередь вместо отказа (3–6-минутные задачи на бесплатной модели → непредсказуемое ожидание; честный отказ понятнее).

## R10 — Тесты и локальный запуск без внешних сервисов

- **Decision**: `@electric-sql/pglite` (devDependency) — настоящий Postgres в процессе. `server/db/index.js`: `DATABASE_URL` → `pg.Pool`; иначе при `NODE_ENV≠production` → PGlite (`memory://` в тестах, `.data/pg` для `npm run dev`); в production без `DATABASE_URL` — отказ старта с понятным сообщением.
- **Проверено спайком 2026-09-19 (PGlite 0.5.8, Node 22)**: `query(sql, params) → {rows}` совпадает с `pg`; работают `$1`-параметры, JSONB/`jsonb_set`, BYTEA, `ON CONFLICT`, `RETURNING`, транзакции. Отличия: BYTEA возвращается как `Uint8Array` (в `pg` — `Buffer`) → оборачивать `Buffer.from`; транзакции — `db.transaction(fn)` против `BEGIN/COMMIT` на клиенте пула → единая обёртка `tx(fn)`.
- **Ограничение**: PGlite занимает ~680 MB RSS и стартует ~5 с → только dev/test, в production запрещён (лимит 0.5 GB). В тестах один экземпляр на файл, таблицы очищаются между тестами.
- **Alternatives considered**: in-memory адаптер с той же сигнатурой (SQL не тестируется — главный риск остаётся непокрытым); Docker-Postgres (не у всех есть, медленнее CI); тестовая ветка Neon (внешняя зависимость и секрет в тестах).

## R11 — Миграции схемы и перенос локальной истории

- **Decision**: SQL-файлы `server/db/migrations/NNN_*.sql`, таблица `schema_migrations`, применение при старте в транзакции. Перенос истории: клиент читает IndexedDB и шлёт анализы по одному в `POST /api/analyses/import` с исходным `id`; сервер делает `INSERT … ON CONFLICT (id) DO NOTHING` → повтор безопасен (FR-017, SC-010). После успеха — флаг `fba_migrated` в localStorage; локальная база не удаляется (страховка), кнопка «Перенести локальную историю» остаётся в «Настройках».
- **Rationale**: один инстанс → гонок миграций нет; клиентские UUID уже используются как id анализа.
- **Alternatives considered**: инструменты миграций (`node-pg-migrate`, Knex) — зависимость ради одного-двух файлов; импорт одним запросом (тело в десятки MB).

## R12 — Совместимость и выпуск

- **Decision**: выпуск по шагам из plan.md; шаг 1 (аккаунты) совместим со старой историей в браузере. Настройки моделей переезжают в `users.settings`; при первом входе значения из localStorage копируются в аккаунт. Экспорт/импорт JSON и автономный HTML не меняются; публичная страница переиспользует тот же код сборки HTML из снимка. CSP остаётся без inline-скриптов (`share.js`, `login.js` — отдельные файлы).
- **Переменные окружения**: новые `DATABASE_URL`, `ADMIN_LOGIN`, `ADMIN_PASSWORD`, `MAX_JOBS`, `PUBLIC_URL` (уже есть); удаляется `APP_PASSWORD`.
- **Деплой**: прежний порядок — GraphQL Railway с `commitSha` при `health.running = 0`.
