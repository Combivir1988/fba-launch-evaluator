# Implementation Plan: Командная работа и публичные ссылки на дашборд

**Branch**: `main` (проект `fba-launch-evaluator/`, собственный git-репозиторий) | **Date**: 2026-09-19 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `fba-launch-evaluator/specs/002-team-accounts-sharing/spec.md`

## Summary

Приложение из однопользовательского (общий пароль, история в браузере) становится командным. Добавляются: личные учётные записи с ролями и сеансами в HttpOnly-cookie; общая история анализов в Postgres (Neon Free) с автором, последним изменившим и оптимистичной блокировкой; публичные ссылки `/s/:token` на неизменяемый снимок дашборда (полный или «без закупочной экономики») с отзывом, сроком и счётчиком просмотров; лимиты одновременных AI-задач и журнал задач. Расчётное ядро `shared/`, рендерер `render.js`, фоновые задачи с SSE-replay и экспорт не меняются по поведению. Инфраструктура остаётся бесплатной: Railway в лимитах Free (0.5 GB RAM, 1 vCPU — уже выставлены) + Neon Postgres Free.

**Testing**: `node --test` — существующие 60 тестов + новые: unit (пароли, сеансы, редактор снимка, лимиты задач), интеграционные на PGlite (миграции, аккаунты, анализы с конфликтом версий, ссылки, журнал), jsdom для публичной страницы, Playwright-пробы (вход → общая история → «Поделиться» → приватное окно)
**Target Platform**: Linux-контейнер Railway (лимиты Free: 0.5 GB RAM, 1 vCPU, один инстанс), браузеры последних 2 версий, публичная страница — от 360 px
**Project Type**: web-service (статика + API) в одном пакете
**Performance Goals**: список истории < 1 с при 2 000 анализов (метаданные в колонках, без чтения документов); открытие анализа < 2 с (+ до 2 с на пробуждение Neon после простоя); публичная страница отрисована < 5 с (SC-004); автосохранение по ползункам — запрос ≤ 60 KB
**Constraints**: $0 инфраструктуры; RAM процесса < 300 MB (измерено сейчас: avg 35 MB, max 192 MB); 0.5 GB БД; один инстанс (задачи в памяти); CSP без inline-скриптов; секреты только в env; в публичном репозитории нет приватных имён
**Scale/Scope**: до 10 пользователей, до 5 одновременно, до ~2 000 анализов; 5 таблиц; ~25 эндпоинтов; 2 новые страницы (вход, публичная) + разделы «Пользователи», «Ссылки», «Журнал задач»

## Ключевые решения (D1–D12)

- **D1 — Хранилище: Postgres на Neon Free, не на Railway.** База на Railway работала бы круглосуточно и съела бы кредит Free ($1/мес); Neon бесплатен бессрочно и засыпает сам. `/api/health` и статика БД не трогают, чтобы база спала. Подробнее — research R1.
- **D2 — Документ делится на `core` (JSONB, ~30–60 KB) и `aggregates_gz` (BYTEA, gzip, ~150–300 KB).** Ползунки и AI меняют только `core` → автосохранение лёгкое; `aggregates` пишутся только при загрузке файлов. Метаданные списка (ниша, ключ, вердикт, C1, score, источники) — отдельные колонки, список не читает документы. Бюджет места: ~0.35 MB на анализ → ≥ 1 300 анализов в 0.5 GB; индикатор заполнения для админа (R2).
- **D3 — Оптимистичная блокировка по `version`.** Сохранение шлёт `baseVersion`; несовпадение → `409` с именем и временем изменившего → диалог «копия / перезаписать / открыть свежую» (FR-015). Блокировок «кто открыл» нет.
- **D4 — Пароли: scrypt (N=2^15, r=8, p=3, соль 16 B, ключ 64 B), параметры в строке хэша.** Хэширование в очереди по одному — потолок ~35 MB RAM при лимите 0.5 GB. Для неизвестного логина выполняется фиктивная проверка — одинаковое время и сообщение (FR-007).
- **D5 — Сеансы: случайный токен 32 B в cookie `fba_sid` (HttpOnly, Secure, SameSite=Lax, 30 дней скользящих), в БД только SHA-256.** Кэш проверки 60 с — и БД не дёргается на каждый запрос, и отключение пользователя действует ≤ 1 мин (FR-008). EventSource сам шлёт cookie → `?token=` из URL исчезает.
- **D6 — CSRF:** SameSite=Lax + для всех изменяющих запросов обязательны `Content-Type: application/json`, заголовок `X-Requested-With: fba` и совпадение `Origin` с хостом.
- **D7 — Первый админ из env** (`ADMIN_LOGIN`, `ADMIN_PASSWORD`) создаётся при старте, если в БД нет ни одного активного администратора; тем же способом владелец восстанавливает доступ. `APP_PASSWORD` удаляется.
- **D8 — Публичная ссылка: токен 32 B base64url в пути `/s/:token`, снимок строится на сервере** чистой функцией `buildSnapshot` и хранится gzip. Снимок не содержит сырых ключей Cerebro (~40 KB gzip). Токен хранится открыто — снимок лежит в той же БД, хэширование ничего не добавляет, зато ссылку можно скопировать повторно.
- **D9 — Режим «без закупочной экономики» — удаление данных, а не скрытие в интерфейсе.** Из снимка вырезаются входы и результаты экономики/бюджета, комментарии критериев 2 и 6 заменяются статусом, тексты AI фильтруются по предложениям; контрольная проверка — поиск числовых значений COGS/маржи/ROI/бюджета в итоговом JSON, при находке поле удаляется целиком. Правила — в `contracts/share-snapshot.md`, тест на SC-006.
- **D10 — Единый ответ для несуществующей, отозванной и истёкшей ссылки** (одна страница, один код 404, одинаковое время), лимит 60 запросов/10 мин на IP для `/s/` и публичного API; `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `robots.txt`.
- **D11 — Результат задачи записывает сервер.** По завершении AI/патентного скана сервер применяет `reconcile` (для AI) и пишет `ai`/`patents` в `core` анализа, увеличивая версию; клиент получает результат по SSE как раньше. Так результат не теряется при закрытой вкладке и виден с другого устройства (FR-016, FR-032). Лимиты: 1 задача типа на пользователя, 1 на анализ, `MAX_JOBS` (по умолчанию 4) на приложение; отказ — `429` с причиной и списком идущих задач.
- **D12 — Локальная разработка и тесты без внешних сервисов:** при отсутствии `DATABASE_URL` и `NODE_ENV≠production` поднимается PGlite (в памяти для тестов, каталог `.data/` для `npm run dev`). В production без `DATABASE_URL` сервер не стартует с понятной ошибкой.

## Порядок внедрения (для /speckit-tasks)

1. **Фундамент:** `server/db`, миграция, PGlite в тестах, `passwords`, `sessions`, `users`, страница входа, замена `APP_PASSWORD` → US1 целиком.
2. **Общая история:** `analyses`, split/join документа, серверная `history.js`, автосохранение, конфликт версий, перенос из IndexedDB → US2.
3. **Ссылки:** `share-snapshot`, `shares`, `/s/:token`, диалог «Поделиться», список ссылок → US3.
4. **Задачи:** лимиты, запись результата сервером, журнал, подхват по анализу → US4.
5. **Выпуск:** справка, quickstart, создание БД Neon и переменных Railway владельцем/мной, деплой при `running=0`, перенос истории владельца.

Каждый шаг выпускается отдельно и не ломает предыдущий; шаг 1 можно выкатить сразу (история временно остаётся в браузере).

## Complexity Tracking

| Отступление | Почему нужно | Почему проще нельзя |
|---|---|---|
| Пересмотр D1 плана 001 («файлы не покидают устройство»): агрегаты отчётов теперь хранятся на сервере | Общая история и открытие анализа с другого устройства невозможны без серверной копии данных | Хранить на сервере только `results` — тогда коллега не сможет пересчитать анализ ползунками и порогами, а это основная функция |
| Внешний сервис БД (Neon) | Постоянное хранилище на Railway Free стоит денег; SQLite на томе привязывает к платному тому и одному хосту | Файл на диске контейнера теряется при каждом деплое |
