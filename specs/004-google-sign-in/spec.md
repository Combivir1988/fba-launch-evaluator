# Feature Specification: Вход и регистрация через Google

**Feature Branch**: `004-google-sign-in` · **Created**: 2026-09-20 · **Status**: Approved 2026-09-20 (владелец выбрал вариант «по приглашению», создал OAuth-клиент и добавил тестовых пользователей)
**Input**: «Возможно ли сделать авторизацию и регистрацию для пользователей через Google?»

## Проблема

Сегодня людей заводит администратор: придумывает логин, генерирует временный пароль, передаёт его, человек при первом входе меняет пароль; забытый пароль сбрасывает администратор. Для небольшой команды это лишние шаги и лишние секреты. У всех участников уже есть аккаунт Google — вход через него убирает пароли из процесса.

Ограничение, которое нельзя потерять: все анализы видны всей команде, а AI работает на одном общем бесплатном ключе. Поэтому «регистрация» не может быть открытой для любого владельца аккаунта Google.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Войти через Google по приглашению (Priority: P1)

Администратор вписывает почту человека. Человек нажимает «Войти через Google», выбирает этот аккаунт — и сразу работает. Паролей нет.

**Independent Test**: админ добавляет почту → человек входит через Google с этой почты и видит общую историю; с другой почты — отказ с понятным сообщением.

**Acceptance Scenarios**:

1. **Given** на сервере настроен вход через Google, **When** открыта страница входа, **Then** на ней есть кнопка «Войти через Google» рядом с формой логина и пароля; если вход через Google не настроен — кнопки нет.
2. **Given** администратор добавил пользователя с почтой и без пароля, **When** этот человек входит через Google с той же почтой, **Then** он попадает в приложение под своим именем; имя по умолчанию берётся из аккаунта Google, если администратор его не задал.
3. **Given** почта аккаунта Google не добавлена администратором, **When** человек пытается войти, **Then** он возвращается на страницу входа с сообщением «этой почты нет в списке приглашённых — попросите администратора добавить её», учётная запись не создаётся.
4. **Given** пользователь отключён администратором, **When** он входит через Google, **Then** вход отклоняется тем же сообщением, что и для неприглашённой почты.
5. **Given** человек уже входил через Google, **When** он позже сменил адрес почты в своём аккаунте Google, **Then** вход продолжает работать: учётная запись привязана к постоянному идентификатору аккаунта Google, а не только к адресу.
6. **Given** человек не завершил вход на стороне Google (закрыл окно, отказал в доступе), **When** он возвращается, **Then** видит страницу входа с нейтральным сообщением и может попробовать снова.

---

### User Story 2 — Управление приглашениями и способами входа (Priority: P1)

**Acceptance Scenarios**:

1. **Given** раздел «Пользователи», **When** администратор добавляет человека, **Then** он указывает имя, почту, роль и выбирает способ: «только через Google» (пароль не создаётся) или «логин и пароль» (как раньше, почта необязательна).
2. **Given** существующий пользователь с паролем, **When** администратор добавляет ему почту, **Then** этот человек может входить и паролем, и через Google.
3. **Given** таблица пользователей, **When** администратор её смотрит, **Then** видны почта и способ входа каждого: «Google», «пароль» или «Google и пароль».
4. **Given** почта уже занята другим пользователем, **When** администратор пытается её назначить, **Then** получает понятный отказ.
5. **Given** пользователь со входом только через Google, **When** он открывает «Настройки», **Then** вместо формы смены пароля видит пояснение, что входит через Google.

---

### User Story 3 — Запасной вход и безопасность (Priority: P1)

**Acceptance Scenarios**:

1. **Given** вход через Google недоступен (сбой Google, потеря доступа к почте), **When** администратор входит логином и паролем, **Then** вход работает как раньше; первый администратор из параметров развёртывания сохраняется.
2. **Given** злоумышленник подсовывает жертве ссылку возврата со своим кодом входа, **When** жертва её открывает, **Then** вход отклоняется: ответ Google принимается только в том браузере, который начинал вход, и только один раз.
3. **Given** ответ, подписанный не Google, выданный для другого приложения, просроченный или с неподтверждённой почтой, **When** сервер его проверяет, **Then** вход отклоняется.
4. **Given** успешный вход через Google, **When** сеанс создан, **Then** он ничем не отличается от сеанса по паролю: та же защищённая cookie, тот же срок, то же мгновенное закрытие при отключении пользователя.
5. **Given** параметр возврата после входа указывает на чужой сайт, **When** вход завершён, **Then** человек попадает на главную страницу приложения.

### Edge Cases

- Регистр и пробелы в почте не важны: `Anna.K@Gmail.com` и `anna.k@gmail.com` — одна почта.
- Приложение Google в режиме «Testing»: войти могут только почты из списка тестовых пользователей в консоли Google; остальные получают отказ ещё на стороне Google.
- Сервер перезапущен между началом и завершением входа — человек видит «попробуйте ещё раз».
- Повторное использование ссылки возврата (кнопка «Назад») — отказ, начать вход заново.
- У последнего администратора вход только через Google — допустимо, но приложение предупреждает, что запасного пароля нет; восстановление — через параметры развёртывания.

## Requirements *(mandatory)*

- **FR-001**: Система MUST предлагать вход через Google на странице входа, когда на сервере заданы параметры клиента Google; иначе кнопка не показывается, остальное работает как раньше.
- **FR-002**: Войти через Google MUST мочь только активный пользователь, чья подтверждённая почта Google совпадает с почтой, заданной администратором, либо чей аккаунт Google уже привязан.
- **FR-003**: Система MUST NOT создавать учётные записи для неприглашённых почт; сообщение об отказе одинаково для неприглашённой почты и отключённого пользователя.
- **FR-004**: При первом входе система MUST привязать постоянный идентификатор аккаунта Google к пользователю и далее опознавать его по нему.
- **FR-005**: Администратор MUST мочь создать пользователя только с почтой (без пароля), задать или изменить почту любому пользователю; почта уникальна без учёта регистра.
- **FR-006**: Вход по логину и паролю MUST оставаться доступным для пользователей, у которых пароль задан; механизм первого администратора сохраняется.
- **FR-007**: Система MUST проверять ответ Google: подпись, издателя, получателя, срок действия, одноразовый номер и признак подтверждённой почты; обмен кода выполняется с защитой от перехвата кода.
- **FR-008**: Начало и завершение входа MUST быть связаны одноразовым значением, привязанным к браузеру; значение действует не дольше 10 минут и только один раз.
- **FR-009**: После входа система MUST возвращать человека только на страницу этого же приложения.
- **FR-010**: Система MUST запрашивать у Google только почту и базовый профиль (имя); доступ к другим данным аккаунта не запрашивается; секрет клиента хранится только на сервере.
- **FR-011**: Журнал сервера MUST фиксировать успешные и отклонённые входы через Google (почта, причина) без кодов, токенов и секретов.
- **FR-012**: Раздел «Пользователи» MUST показывать почту и способ входа; «Настройки» пользователя без пароля не предлагают смену пароля.
- **FR-013**: Справка MUST описывать вход через Google, приглашение по почте и запасной вход.

### Key Entities

- **Пользователь** (расширение): почта (необязательная, уникальная), идентификатор аккаунта Google (необязательный, уникальный), признак «пароль задан».
- **Попытка входа через Google**: одноразовое значение, привязка к браузеру, срок 10 минут, адрес возврата внутри приложения.

## Success Criteria *(mandatory)*

- **SC-001**: Приглашённый человек попадает в приложение за 2 нажатия и меньше чем за 15 секунд, не вводя ни одного пароля.
- **SC-002**: Администратор добавляет человека со входом через Google, заполнив 3 поля (имя, почта, роль).
- **SC-003**: 100 % попыток входа с неприглашённой почты отклоняются без создания учётной записи.
- **SC-004**: 100 % подделанных, чужих, просроченных и повторных ответов отклоняются (проверяется автотестами).
- **SC-005**: Существующие пользователи с паролем входят как раньше; все прежние тесты остаются зелёными.

## Assumptions

- Вариант регистрации — «по приглашению»: выбран владельцем как рекомендованный; открытая регистрация и очередь на одобрение — вне объёма.
- Клиент Google создан владельцем (проект `fba-launch-evaluator`, тип Web application), адреса возврата: прод и `http://localhost:3000`; параметры лежат в файле секретов.
- Приложение Google пока в режиме «Testing» со списком тестовых пользователей; публикация — решение владельца, кода не меняет.
- Другие провайдеры входа (Microsoft, Apple), двухфакторная проверка и самостоятельное удаление аккаунта — вне объёма.
- Незавершённые попытки входа хранятся в памяти одного экземпляра сервера; при перезапуске человек просто начинает вход заново.
