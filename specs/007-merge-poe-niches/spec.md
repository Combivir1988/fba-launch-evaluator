# Feature Specification: Несколько POE-файлов в одном анализе — объединение ниш

**Feature Branch**: `007-merge-poe-niches` · **Created**: 2026-09-21 · **Status**: Approved 2026-09-21 (владелец выбрал вариант «объединить»)

## Проблема

Amazon в Product Opportunity Explorer часто делит один рынок на несколько ниш («amaranthus artificial flower», «hanging amaranthus garland» и т. п.). Один POE-файл видит только часть рынка: часть товаров, часть запросов, часть кликов. Сейчас в анализе может быть только один POE — второй файл молча заменяет первый, без предупреждения. В результате конверсия клика, доли кликов, когорта новичков и «продажи на 1 % кликов» считаются по куску рынка, а менеджер об этом не знает.

## User Scenarios & Testing

### User Story 1 — Загрузить несколько ниш и получить общий рынок (Priority: P1)

Менеджер перетаскивает два–пять POE-файлов (сразу или по одному) и видит один дашборд по объединённому рынку.

**Independent Test**: загрузить два POE разных ниш → в списке файлов две карточки POE, в шапке «POE · 2 ниши», доли кликов и конверсия клика пересчитаны по общему рынку; удалить одну карточку → анализ возвращается к одной нише.

**Acceptance Scenarios**:

1. **Given** в анализе уже есть POE, **When** менеджер загружает POE другой ниши, **Then** файл добавляется, а не заменяет прежний; анализ считается по объединённым данным; сообщение говорит «добавлена ниша … — теперь объединено N».
2. **Given** загружен POE той же ниши повторно (тот же идентификатор ниши), **When** файл обработан, **Then** он обновляет эту нишу, а не дублирует её; сообщение говорит «ниша обновлена».
3. **Given** объединено несколько ниш, **When** менеджер смотрит список файлов, **Then** у каждой ниши своя карточка (название, число товаров, доля кликов в общем рынке) с кнопкой удаления; удаление одной ниши пересчитывает анализ по оставшимся.
4. **Given** товар есть в нескольких нишах, **When** данные объединяются, **Then** он учитывается один раз: клики складываются, доля кликов считается от суммы кликов всех ниш.
5. **Given** запрос есть в нескольких нишах, **When** данные объединяются, **Then** он учитывается один раз: объём поиска берётся один раз (это одни и те же поиски), клики по нему складываются.
6. **Given** объединённый анализ, **When** открыт дашборд, **Then** в шапке видно, что POE объединён из N ниш, и перечислены ниши с их весом; в пометках о данных сказано, какие показатели сложены, какие пересчитаны, а какие взяты приближённо.
7. **Given** старый анализ с одним POE, **When** он открыт и к нему добавлен второй POE, **Then** прежний POE становится первой нишей объединения без повторной загрузки.

### User Story 2 — Честность сводных показателей (Priority: P1)

**Acceptance Scenarios**:

1. **Given** недельные тренды ниш, **When** они объединяются, **Then** складываются только недели, присутствующие во всех нишах (иначе появились бы ложные провалы сезонности); если общих недель меньше минимума для сезонности — берётся тренд самой крупной ниши с пометкой.
2. **Given** счётные показатели ниш (товары, бренды, продавцы, запуски, успешные запуски), **When** объединяются, **Then** складываются; успешность запусков считается как сумма успешных ÷ сумма запусков.
3. **Given** средние показатели ниш (средние отзывы, рейтинг, цена, доля спонсорских, отсутствие в наличии, возвраты), **When** объединяются, **Then** берётся среднее, взвешенное по кликам ниш.
4. **Given** доли кликов топ-брендов и топ-товаров, **When** объединяются, **Then** пересчитываются по объединённому списку товаров, а значения «квартал назад / год назад» для них не показываются (их нельзя восстановить).
5. **Given** темы отзывов, **When** объединяются, **Then** одноимённые темы сливаются со взвешенной долей упоминаний.
6. **Given** один POE-файл, **When** анализ считается, **Then** результаты те же, что до этой доработки.

### User Story 3 — Везде, где живёт анализ (Priority: P2)

**Acceptance Scenarios**:

1. **Given** объединённый анализ, **When** он сохранён и открыт заново (или другим человеком из общей истории), **Then** все ниши на месте и любую можно удалить.
2. **Given** объединённый анализ, **When** создана публичная ссылка или скачан HTML, **Then** дашборд показывает объединённые данные и пометку об объединении; исходные файлы ниш в ссылку и HTML не попадают (они не нужны для просмотра).
3. **Given** объединённый анализ, **When** запущен AI-анализ, **Then** AI знает, что рынок собран из нескольких ниш и какие показатели приближённые.

### Edge Cases

- Ниши почти полностью совпадают по товарам (одна вложена в другую): объединение работает, в пометках показана доля общих товаров и предупреждение, что клики по общим запросам могут быть учтены дважды.
- У ниши нет счётчиков кликов по товарам — её вес берётся по объёму поиска ниши; если нет и его — веса равные; это названо.
- Файлы сняты в разные дни: опорная дата возраста листингов — самая поздняя дата снятия; разница больше 30 дней названа в пометках.
- Загружено больше 8 ниш — лишние отклоняются с понятным сообщением (объём данных анализа ограничен).
- Кнопка удаления у последней оставшейся ниши убирает POE целиком.

## Requirements

- **FR-001**: Анализ MUST принимать несколько POE-файлов; новый файл другой ниши добавляется, файл той же ниши обновляет её.
- **FR-002**: Система MUST объединять товары и запросы без дублей по правилам сценариев US1.4–1.5 и пересчитывать доли кликов от суммы кликов всех ниш.
- **FR-003**: Система MUST объединять сводные показатели по правилам US2 и не показывать то, что восстановить нельзя.
- **FR-004**: Система MUST показывать состав объединения (ниши, число товаров, вес по кликам, общие товары и запросы) в списке файлов, в шапке дашборда и в пометках о данных.
- **FR-005**: Каждую нишу MUST можно удалить отдельно; анализ пересчитывается по оставшимся.
- **FR-006**: С одним POE-файлом результаты расчёта MUST совпадать с прежними (контрольные отпечатки).
- **FR-007**: Объединённый анализ MUST сохраняться в общей истории со всеми нишами, открываться у других людей, экспортироваться и импортироваться; старые анализы с одним POE открываются без изменений.
- **FR-008**: Публичная ссылка и автономный HTML MUST содержать объединённые данные и пометку, но не исходные ниши по отдельности.
- **FR-009**: AI MUST получать состав объединения и перечень приближённых показателей.
- **FR-010**: Справка дополняется.

## Success Criteria

- **SC-001**: Для двух ниш без общих товаров суммарные клики объединённого рынка равны сумме кликов ниш, а доли кликов всех товаров в сумме дают то же, что давали бы веса ниш (сверка ручным расчётом).
- **SC-002**: Товар и запрос, присутствующие в двух нишах, в объединённых списках встречаются ровно один раз.
- **SC-003**: Удаление добавленной ниши возвращает результаты, совпадающие с анализом по одной исходной нише.
- **SC-004**: С одним POE контрольные отпечатки расчёта не меняются.
- **SC-005**: Объединение пяти ниш пересчитывается быстрее секунды.

## Assumptions

- Объём поиска запроса — свойство запроса, а не ниши: у одного и того же запроса в разных нишах он одинаков, поэтому берётся один раз (максимум из значений).
- Конверсия поиска запроса при совпадении берётся максимальная, а не суммируется: так оценка конверсии клика объединённого рынка не завышается.
- Клики товара в нише — клики с запросов этой ниши. Если ниши делят запросы, часть кликов общих товаров может быть учтена дважды; точно разделить их по данным POE нельзя — это названо в пометках.
- Текстовые выводы Amazon (Insights) берутся из самой крупной по кликам ниши.
- Xray, Cerebro и SQP остаются по одному файлу: Xray и Cerebro и так снимаются по всему рынку.
