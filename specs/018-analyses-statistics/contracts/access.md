# Контракт: право на раздел «Статистика»

Новых маршрутов для доступа не заводится — расширяются два существующих.

## `PATCH /api/users/:id` (админский, уже есть)

К белому списку `{ name, role, active, email }` добавляется `statsAccess: boolean`.

```json
{ "statsAccess": true }
```

| Правило | Почему |
|---|---|
| Маршрут уже под `admin` (`requireAdmin` + `requirePasswordChanged`) | FR-003: выдаёт только администратор |
| Значение пишется в колонку `users.stats_access`, не в `settings jsonb` | D6: `settings` пишет сам пользователь |
| Менять себе — можно, но бессмысленно: админ имеет право всегда | допущение спеки |
| Каждое изменение пишется в журнал приложения: `log("info", "stats access changed", { by, user, to })` | FR-005 — кто, кому, когда, в какую сторону |

Снятие права **не** рвёт сеанс: право проверяется на каждом запросе данных, поэтому закрывается не позже следующего обращения (FR-004, SC-008). Отдельного «выкинуть из раздела» не требуется.

## `GET /api/auth/me` (уже есть)

В объект пользователя добавляется `statsAccess: boolean` — вычисленное право (`role === "admin" || stats_access`), а не сырая колонка.

Браузер по нему решает, показывать ли кнопку раздела. **Это удобство, а не защита**: кнопку можно дорисовать руками, данные всё равно отдаёт только сервер и только по праву.

## `GET /api/users` (админский, уже есть)

В строке пользователя появляется `statsAccess`, чтобы в «Настройки → Пользователи» было видно, у кого право есть, и стояла кнопка его переключения.

## Проверка права на сервере

Одно место, не повторяемое по маршрутам:

```
requireStats = [requireUser, requirePasswordChanged, (req, res, next) =>
  req.user.role === "admin" || req.user.statsAccess ? next()
    : res.status(403).json({ error: "no_stats_access", message: "Раздел «Статистика» вам не открыт" })]
```

Отказ не содержит ни одной цифры статистики (FR-002).
