# Implementation Plan: возвраты в экономике и план запуска

**Feature**: `020-returns-and-launch-plan` · **Branch**: `main` · **Дата**: 2026-11-12
**Спека**: [spec.md](./spec.md) · **Артефакты**: [research.md](./research.md) · [data-model.md](./data-model.md) · [contracts/formulas.md](./contracts/formulas.md) · [quickstart.md](./quickstart.md)

## Summary

Четыре добавления из разбора Amazon New Product Success Playbook. Все считаются из данных, которые уже лежат в анализе; миграции базы нет.

**Первое — починка, а не улучшение.** Доля возвратов читается из отчёта, показывается плиткой в обзоре и **не участвует в расчёте прибыли ни разу** (проверено: в файле экономики слово «возврат» встречается ноль раз). Для ниши с 8–12 % возвратов это разница между «экономика сходится» и «не сходится», то есть решение о закупке партии принимается по завышенной марже.

Модель выбрана самая строгая (решение господаря): возвращённый товар списывается целиком. При таких умолчаниях формула сводится к одной фразе — **каждый возврат стоит ровно той чистой выручки, которую продажа должна была принести**.

Остальные три отвечают на вопросы, которые гайд считает обязательными до закупки: по каким значениям я пойму, что запуск идёт не так; хватит ли денег; есть ли вообще место новичку в этой структуре рынка.

**Что выяснилось при планировании и изменило спеку.** Исходное допущение — «пессимистичному сценарию нужно больше денег» — оказалось неверным. Замер на контрольных данных: быстрый рост требует пика **$9 163**, ожидаемый $8 643, медленный **$7 586**. Самый дорогой сценарий — успех: товар расходится, дозаказы чаще и крупнее, касса кончается в тот момент, когда всё получается. Требование и критерий исправлены до того, как под неверное утверждение был написан тест.

## Constitution Check

`.specify/memory/constitution.md` в этом рабочем пространстве — незаполненный шаблон. Формальных ворот из конституции нет.

Вместо них план держится правил репозитория:

| Правило | Как соблюдено |
|---|---|
| Расчёт — чистые функции в `shared/`, общие для браузера и тестов | всё считается там же, где считается сейчас, без доступа к базе и сети |
| Тесты на ядро первыми | ворота SC-002 и SC-004 пишутся до реализации |
| Публичный репозиторий — без следов сторонних брендов | базовый замер хранит порядковые номера и числа, без названий ниш |
| Справка обновляется в том же коммите | карточка входит в объём (FR-028) |
| Не ломать соседнее | ниши без возвратов обязаны остаться нетронутыми — это ворота, а не пожелание |
| Приватность важнее удобства | новых типов данных наружу не уходит |

Нарушений, требующих оправдания, нет — раздел «Complexity Tracking» пуст и удалён.

**Structure Decision**: возвраты и сценарии встраиваются в существующие модули — там, где уже живут прибыль и помесячные деньги. План измерений и структура рынка выносятся в отдельные модули ядра, потому что это новые сущности со своими правилами, но рисуются они **общим рендером**, а не отдельным файлом: FR-016 требует, чтобы план уезжал в автономный файл и по публичной ссылке. Это ровно противоположно решению spec 018, где раздел статистики намеренно вынесен из общего рендера, чтобы НЕ попадать в экспорт.

## Порядок работ

Очерёдность продиктована воротами и механизмом устаревания.

1. **Базовый замер.** Снять с живой базы чтением, положить фикстурой без названий ниш. **До первой правки в `shared/`** (D12). Заодно узнать, у скольких анализов доля возвратов вообще известна — от этого зависит, насколько заметным будет сдвиг.
2. **Ворота 2 (SC-004) тестом.** Неизвестная доля возвратов не превращается в ноль. Тест обязан упасть на реализации через подстановку нуля.
3. **Возвраты в экономике.** `netGross`, `returnCost`, прибыль после возвратов — в одном месте. Тождество формулы тестом.
4. **Ворота 1 (SC-002).** Контрольный отпечаток: ниши без возвратов не изменились ни на копейку. Добавочные поля из отпечатка исключить до сравнения.
5. **Запас и сценарии.** Закупать больше на долю потерь; три прогона; точка дозаказа; предупреждение о бюджете по самому требовательному сценарию.
6. **Структура рынка.** Направление из отчёта с историей, уровень из отчёта по листингам, отказ без первого.
7. **План измерений.** Пороги из посчитанного, ритм разбора, таблица диагностики.
8. **Интерфейс.** Стоимость возвратов в экономике, сценарии в помесячных деньгах, новая секция плана, вывод о структуре; подписи порогов, подсказки.
9. **Наружу.** Факты для AI, автономный файл, публичная ссылка.
10. **Справка**; проверки 4–8 из quickstart на живых данных.

MVP — пункты 1–4: починенная экономика, запертая обоими воротами. Остальное добавляется сверху и ничего не ломает.

## Чего план сознательно не делает

- Не трогает режим «ожидает COGS»: пока себестоимость не введена, экономика не считается вовсе, и возвраты в ней не участвуют.
- Не переписывает сохранённые результаты прежних анализов — расхождение показывает раздел «Статистика» (FR-029).
- Не меняет цель продаж в сценариях: отличается только скорость выхода на неё (D6).
- Не выводит направление концентрации из уровня: уровень — снимок и зависит от глубины вывозки (D9).
- Не собирает фактические данные после запуска. План измерений называет, за чем следить; сами показатели человек смотрит в своём аккаунте продавца.
- Не заводит миграции и не зеркалит функцию в saas.
