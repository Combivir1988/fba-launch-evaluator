# Контракт: формулы и правила

Договор между расчётом и всем, что его читает. Записан так, чтобы по нему можно было написать тест, не заглядывая в код.

---

## 1. Возвраты

### Обозначения

| | что это | откуда |
|---|---|---|
| `r` | доля возвратов | отчёт ниши или ручной ввод; **может отсутствовать** |
| `resalable` | доля возвращённого товара, пригодного к перепродаже | порог, по умолчанию **0** |
| `returnFee` | сбор за обработку возврата | порог, по умолчанию **0** |
| `price` | цена | ввод |
| `referral` | комиссия маркетплейса, долей | ввод |
| `cogs`, `ship`, `fba` | себестоимость, доставка до склада, сбор за отправку | ввод |

### Прибыль на единицу

```
netGross = price − cogs − ship − price × referral − fba        (то, что считалось раньше)

returnCost = r × ( netGross + fba + returnFee + (1 − resalable) × (cogs + ship) )

net = netGross − returnCost
```

`net` — прибыль на единицу, которой пользуются ВСЕ остальные расчёты: маржа, ROI, статус Gate 1, сетка Gate 2, безубыточный CVR, ось экономики, пограничные значения.

### Обязательное тождество

При `resalable = 0` и `returnFee = 0`:

```
returnCost = r × price × (1 − referral)
```

Это не приближение, а точное равенство. Тест обязан проверять его на нескольких наборах чисел: оно ловит и ошибку в общей формуле, и подмену умолчаний.

### Правило отсутствия

```
если r не задано:
    returnCost = отсутствует
    net = netGross
    признак «возвраты не учтены» = истина
```

**Подставлять ноль вместо отсутствия запрещено.** «Возвратов нет» и «мы не знаем, сколько возвратов» — разные утверждения, и второе приложение делать не вправе.

При `r = 0` признак «возвраты не учтены» ложен, `returnCost = 0`, и все числа совпадают с прежними до копейки.

### Что отдаётся наружу

`r`, источник значения (отчёт или ручной ввод), `returnCost`, `netGross`, `net`, признак «возвраты не учтены».

### Границы

- `r` принимается в пределах от 0 до 1. Значение выше 0,5 принимается, но помечается как подозрительное.
- `net` может стать отрицательным — это допустимый результат, он показывается как есть.
- Режим «ожидает COGS» не меняется: пока себестоимость не введена, экономика не считается вовсе, и возвраты в ней не участвуют.

## 2. Запас с учётом возвратов

```
lossRate = r × (1 − resalable)              доля безвозвратно потерянных единиц
unitsToShip = unitsSold / (1 − lossRate)    отгрузить, чтобы продать unitsSold
```

При `r` отсутствующем `lossRate = 0` и всё считается как раньше.

Цель `unitsPerDay` — это **проданные** единицы. Закупка, партии, остаток запаса и точка дозаказа считаются от `unitsToShip`.

**Контрольные значения** (цель 10 шт/день, контрольные данные 2026-11-12):

| `r` | отгружать в день | закуплено | пик вложений |
|---|---|---|---|
| 0 % | 10,00 | 2 850 | $8 643 |
| 5 % | 10,53 | 3 000 | $8 828 |
| 10 % | 11,11 | 3 167 | $9 320 |
| 20 % | 12,50 | 3 563 | $10 806 |

## 3. Сценарии продаж

Три прогона помесячной модели. Отличается только длительность выхода на целевые продажи; сама цель общая.

```
разгон(медленный)  = разгон(ожидаемый) × slowFactor      порог, по умолчанию 1,5
разгон(ожидаемый)  = как задано
разгон(быстрый)    = разгон(ожидаемый) × fastFactor      порог, по умолчанию 0,6
```

У каждого сценария считаются: пик вложений, месяц пика, месяц возврата денег, число партий, закуплено единиц.

**Что измерено и чего ждать** (контрольные данные, цель 10 шт/день):

| сценарий | разгон | пик вложений | возврат денег |
|---|---|---|---|
| быстрый | 4 мес | **$9 163** | месяц 12 |
| ожидаемый | 6 мес | $8 643 | месяц 13 |
| медленный | 9 мес | $7 586 | месяц 13 |

**Самый требовательный к деньгам — быстрый рост.** Это не опечатка и не особенность фикстуры: медленные продажи означают более редкие и меньшие дозаказы.

### Предупреждение о бюджете

```
если бюджет задан и бюджет < max(пик по всем сценариям):
    предупредить, назвать нехватку числом и назвать сценарий
```

Проверять только медленный сценарий запрещено: он как раз самый дешёвый.

## 4. Точка дозаказа

```
leadDays = productionDays + shippingDays + receivingDays       уже считается
reorderAtDays  = leadDays + safetyDays                          safetyDays — порог
reorderAtUnits = reorderAtDays × текущая скорость продаж в день
```

Отдаётся и в днях, и в штуках. При `leadDays = 0` точка вырождается — показывается объяснение, а не ноль.

## 5. Пороги плана измерений

Каждый порог считается из показателя анализа, и источник отдаётся вместе со значением.

| порог | формула | источник |
|---|---|---|
| конверсия, ниже которой продажи в минус | безубыточный CVR | экономика, после возвратов |
| расход на рекламу, выше которого прибыль съедена | `net / price` | экономика, после возвратов |
| запас, ниже которого пора дозаказывать | `reorderAtDays` | помесячная модель |
| планка отзывов и срок до неё | как считается сейчас | расчёт входа в нишу |
| сессий, прежде чем судить о конверсии | порог, значение из гайда | не выводится из экономики — это вопрос достоверности |

Если экономика не посчитана, пороги, зависящие от неё, не показываются, и названо, чего не хватает.

## 6. Структура рынка

```
направление спроса        = рост поискового объёма за год (отчёт с историей)
направление концентрации  = доля топ-5 брендов сейчас против значения год назад (отчёт с историей)
уровень концентрации      = показатель концентрации ниши (отчёт по листингам)

вывод:
  спрос растёт и концентрация падает   → есть место для входа
  спрос растёт и концентрация растёт   → лидеров труднее подвинуть
  уровень концентрации низкий          → сильная фрагментация: место есть, но лояльности мало
  отчёта с историей нет                → вывод НЕ делается
```

Под выводом обязаны стоять все три числа.

**Строить направление концентрации из уровня запрещено**: уровень считается по текущему срезу листингов, истории не имеет, и зависит от глубины вывозки.

---

## 7. Чего расчёт делать не имеет права

- Подставлять ноль вместо неизвестной доли возвратов.
- Менять числа ниш, у которых доля возвратов равна нулю или неизвестна.
- Переписывать сохранённые результаты прежних анализов.
- Делать вывод о структуре рынка без отчёта с историей.
