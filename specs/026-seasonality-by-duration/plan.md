# Implementation Plan: Сезонность по длительности, а не по крайностям

**Branch**: `main` (работа ведётся без отдельной ветки, как и предыдущие спеки) | **Date**: 2026-11-17 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/026-seasonality-by-duration/spec.md`

## Summary

Подпункт 1g Критерия 1 перестаёт мерить «лучшая неделя против худшей» и начинает мерить **долю истории, которую ниша провела в просадках** — отрезках не короче двух недель подряд, где спрос ниже 70 % медианы ряда. Рядом с оценкой появляются три объясняющих величины: средняя глубина просадок, период самой длинной просадки в месяцах и число просадок.

Расчёт выносится в новый чистый модуль `shared/seasonality.js`; `criterion1.js` его вызывает. Пороги статуса переименовываются (`seasonDownOk` / `seasonDownFail`), чтобы старые личные наборы с `seasonOk` не получили **то же имя при другом смысле**. Хранения нет, миграции нет, новых зависимостей нет.

Работа **намеренно смягчает методику** и это измерено: статус 1g `ok 1 · warn 14 · fail 51` → `ok 47 · warn 7 · fail 12`, лучше становится 53 нишам, хуже — ни одной.

## Что решено — коротко

Полные обоснования и числа — в [research.md](research.md).

| № | Решение | Главное число |
| --- | --- | --- |
| **D1** | «Обычный уровень» — **медиана** ряда | одна неделя втрое выше пика сдвигает медиану на **0,37 %**, усечённое среднее на 1,08 %, простое среднее на **8,55 %** |
| **D2** | «Ниже обычного» — ниже **70 %** медианы | при 85 % ровных ниш остаётся 1 из 66 (мера слепнет), при 50 % — 55 из 66 (перестаёт ловить сезонные) |
| **D3** | Просадка — не короче **2 недель подряд** | статус не меняется ни у одной ниши, но ровных становится **31 → 43**; и только так ворота SC-001 верны при любой длине истории |
| **D4** | Статус — по **суммарной доле** истории в просадках; самая длинная просадка и их число — объясняющие | расхождение двух мер: медиана **0,0 п.п.**, максимум 13,5 п.п. |
| **D5** | Пороги **ok < 8 % · fail > 20 %** | `ok 47 · warn 7 · fail 12`; лучше 53 · без изменений 13 · **хуже 0** |
| **D6** | Глубина — **средняя** глубина недель в просадках | медиана совпадает с «самой глубокой неделей» (31 %), но не зависит от одной недели |
| **D7** | Период — **месяцы самой длинной просадки** диапазоном + число просадок | месяцев в самой длинной просадке: медиана 1, максимум 6 |
| **D8** | Расчёт — **новый `shared/seasonality.js`** | `method_hash` меняется в любом случае: `criterion1.js` правится |
| **D9** | Пороги **переименовываются** | иначе старый личный набор `seasonOk: 0.25` молча означал бы «четверть года внизу — это ок» |
| **D10** | `borderline.js` следует новой мере | образец — 1d из spec 022, тот же файл, строки 22–26 |
| **D11** | Отпечаток сужается **до** правки расчёта | образец — spec 019 и spec 022 в `results-hash.js` |
| **D12** | Базовый замер — **первой задачей** | `method_hash` = sha256 по всем `shared/*.js` |
| **D13** | `compute.js` не правится | 1g копируется целым объектом строкой 56, новые поля едут сами |

## Порядок работ

1. **T-база. Базовый замер «до»** — до единой правки в `shared/`. Чтение живой базы без единой записи: значение и статус 1g, `okCount` и `pass` Критерия 1, ось рынка Scorecard, вердикт, контрольный отпечаток. Фикстура `tests/fixtures/season-baseline.json` **без названий ниш**.

2. **Ворота SC-004 — сужение отпечатка.** В `tests/helpers/results-hash.js` исключить **добавочные** поля сезонности (`downShare`, `depth`, `months`, `dips`, `longest`, `lowOf`) с комментарием в том же стиле, что уже есть для спек 019, 020, 022. Намеренное изменение (значение и статус 1g, `okCount`) из отпечатка **не исключается** — оно обязано быть видно. Делается **до** правки расчёта, чтобы падение отпечатка имело одну причину, а не две.

3. **Ворота SC-001…SC-003 тестами, до реализации.** `tests/seasonality.test.js`: одноразовый всплеск и одна мёртвая неделя не меняют статус при любой длине истории; летний товар остаётся `fail`; история короче минимума даёт `na`, а доля считается от фактической длины.

4. **Ядро: `shared/seasonality.js`.** Чистая функция: ряд недель → медиана, флаги «ниже 70 %», склейка в просадки от 2 недель, суммарная доля, самая длинная просадка, средняя глубина, месяцы, число просадок. Никаких статусов внутри — только числа.

5. **`shared/criterion1.js`.** Подпункт 1g вызывает `seasonality()`, статус по новым порогам, примечание пишет человеческую фразу с долей, глубиной и периодом.

6. **`shared/thresholds.js`.** Новые ключи, старые убраны. Проверить, что `thresholdOverrides` действительно отбрасывает ключ, которого нет в умолчаниях.

7. **`shared/borderline.js`.** Две записи 1g переводятся на новую величину и новые пороги.

8. **Интерфейс и тексты.** Подсказки к трём новым величинам, подписи порогов во вкладке «Пороги», карточка в Справке: **почему** мера сменилась и что потеряли владельцы личных наборов.

9. **Живая проверка после развёртывания** — девять проверок quickstart со сверкой по базовому замеру.

**MVP = пункты 1–7.** Без восьмого отчёт считает правильно, но молчит о причине.

## Чего делать не будем

Из спеки, подтверждено замерами:

- **Скользящая средняя** — замерено, медиана 50 %, задачу не решает (чинить надо точку отсчёта, а не шум).
- **Пороги по классу товара** — у нас нет классификации товаров, на которую их вешать.
- **Месячная и квартальная агрегация** вместо недельной.
- **Прогноз спроса** на будущие недели.
- **Привязка закупки партии к месяцу просадки** — это бюджет, его не трогаем.
- **Сезонность по кликам** вместо поискового объёма.
- **Зеркало в saas.**
