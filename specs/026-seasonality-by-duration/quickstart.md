# Quickstart: проверка spec 026 (сезонность по длительности)

Девять проверок. Первые четыре — **ворота**: каждые проверяются подлогом, то есть намеренно неправильной реализацией, на которой тест обязан упасть. Ворота, которые не падают при подлоге, ничего не доказывают — это уже случалось в spec 025 дважды.

---

## Перед началом

**Проверка 0 — базовый замер снят до единой правки в `shared/`.**

```bash
node .data/baseline-026.mjs
```

Ожидается `tests/fixtures/season-baseline.json` **без названий ниш**, в нём по каждому живому анализу: значение и статус 1g, `okCount` и `pass` Критерия 1, оценка рыночной оси Scorecard, вердикт, контрольный отпечаток.

Если базовый замер снят **после** правки в `shared/`, он недействителен: `method_hash` пересчитает сохранённые итоги текущим кодом, и прежних цифр не останется. Переснять будет неоткуда.

---

## Ворота

### SC-001 — одноразовый всплеск ничего не решает

**Что проверяем.** Ряд из 52 недель ровного спроса даёт некоторый статус. Добавление одной недели втрое выше обычного статус не меняет. Добавление одной мёртвой недели статус не меняет. **То же самое на истории в 11 недель** — именно там правило ломается, если его написать наивно.

```bash
node --test tests/seasonality.test.js
```

**Подлог.** Заменить меру на прежнюю:

```js
// в shared/criterion1.js вместо вызова seasonality():
const peak = Math.max(...svs), trough = Math.min(...svs);
it.value = (peak - trough) / peak;
```

Тест обязан упасть — и упасть **именно на пунктах про всплеск**, а не на летнем товаре.

**Второй подлог, отдельный.** Убрать минимальную длину просадки (`minRun = 1`). Тест обязан упасть **только на коротком ряде** (11 недель, одна мёртвая неделя → 9,1 % → статус переворачивается), а на длинном пройти. Если падает и на длинном — фикстура собрана неверно.

---

### SC-002 — настоящая сезонность остаётся «не ок», подпункт не зеленеет для всех

**Что проверяем.**

1. Летний товар (26 недель по 1000, затем 26 по 300) даёт `fail`.
2. На полном наборе живых анализов среди статусов 1g присутствуют **и `ok`, и `fail`**, и ни одна из групп не единична.

```bash
node --test tests/seasonality.test.js
node .data/after-026.mjs      # живая часть
```

**Подлог.** Поднять `seasonDownFail` до `0.95`. Тест обязан упасть на летнем товаре.

**Второй подлог.** Опустить `seasonDownOk` до `0.0001`. Тест обязан упасть на требовании «группа `ok` не единична» — то есть ворота ловят вырождение в обе стороны, а не только в одну.

---

### SC-003 — короткая история не судится и не умножается

**Что проверяем.**

1. История в 6 недель → статус `na` с названной причиной, **не** `fail`.
2. История в 12 недель с просадкой в 2 недели → доля `2/12 = 16,7 %`, а не `2/52 = 3,8 %`.

```bash
node --test tests/seasonality.test.js
```

**Подлог.** Поделить на 52 вместо фактической длины:

```js
downShare = downWeeks / 52;
```

Тест обязан упасть на коротком ряде и пройти на полном — так видно, что проверяется именно знаменатель.

---

### SC-004 — сдвинуться разрешено только сезонности, Scorecard и вердикту

**Что проверяем.** На всех фикстурах совпадают с состоянием «до»: экономика, конкуренция, трафик, вход в нишу, цена конфигурации, распределение цен, товарная линейка, план измерений, патенты, этап 3.

```bash
node --test tests/results-hash.test.js
node --test
```

**Пишется первой задачей, до правки расчёта.** Иначе первый же прогон уронит отпечаток, и причину («задето лишнее» или «просто добавились поля») пришлось бы выяснять задним числом.

**Чего здесь НЕТ и почему.** Привычных ворот «контрольный отпечаток не сдвинулся» здесь быть не может: подпункт 1g меняется намеренно, значит отпечаток обязан сдвинуться. Ворота в такой формулировке ничего не сказали бы. Поэтому из отпечатка исключается **поимённый** список добавочных полей — `downShare`, `depth`, `months`, `dips`, `longest`, `lowOf` — а значение и статус 1g вместе с `okCount` Критерия 1 **остаются** и обязаны сдвиг показать. Приём повторяет решения spec 019 и spec 022, записанные в самом `results-hash.js`.

**Подлог.** Добавить любое из добавочных полей обратно в отпечаток — отпечаток сдвинется у **всех** ниш, включая те, где статус не изменился, и это видно по числу расхождений.

## Проверки на живых данных

### Проверка 5 — распределение статусов

```bash
node .data/after-026.mjs
```

| Что | Было | Ожидается |
| --- | --- | --- |
| Статусы 1g | `ok 1 · warn 14 · fail 51` | `ok 47 · warn 7 · fail 12` |
| Ровных ниш со статусом не-`ok` | 19 из 31 | **0** |
| Десять самых сезонных (23…46 % года внизу) | `fail` | **все `fail`** |
| Ниш, получивших **худший** статус | — | **0** |

Расхождение больше чем на четверть — повод остановиться и разобраться, **а не исправить ожидание**.

### Проверка 6 — сдвиг Критерия 1 и вердиктов

| Что | Было | Ожидается |
| --- | --- | --- |
| Критерий 1 проходят | 9 из 68 | больше; число называется замером |
| Вердикты | `No-Go 46 · Доработка 17 · Go 2 · Go условно 3` | сдвиг называется числом |
| Вердиктов стало **хуже** | — | **0** |

**Замер сдвига вердиктов — только двумя отдельными процессами.** Внутри одного процесса `compute.js` тянет `criterion1.js` статическим импортом, модуль берётся из кэша, подстановка не подхватывается и замер даёт **ложный ноль**. Так уже ошиблись в spec 022.

### Проверка 7 — объясняющие числа на месте

Открыть анализ сезонной ниши (например, с просадкой в августе) и убедиться, что рядом со статусом названы:

- сколько недель и какая доля истории ниже обычного спроса;
- средняя глубина просадок;
- период самой длинной просадки словами («август» или «с июня по сентябрь»);
- число просадок, если их больше одной.

Открыть ровную нишу и убедиться, что сказано «просадок нет», а месяц **не выдуман**.

### Проверка 8 — отчёт говорит об одном одинаково

1. Блок пограничных значений называет ту же величину и те же пороги, что и подпункт.
2. Во вкладке «Пороги» подписи соответствуют новым ключам.
3. Подсказки при наведении есть у всех новых величин и не длиннее 330 знаков:

```bash
node --test tests/tips.test.js
```

4. Личный набор порогов со старым `seasonOk` открывается без ошибки, старый ключ отбрасывается, применяются новые умолчания. Потеря названа в Справке.

### Проверка 9 — ценовой коридор

Открыть анализ с заданным ценовым коридором и убедиться, что подпункт 1g показывает те же числа, что и без коридора (спрос от цены не зависит), и что объясняющие поля на месте — они едут вместе с объектом подпункта.
